## 1. Overview

RentaCar is a full-stack car rental management platform built for Moroccan rental businesses. It covers the complete rental lifecycle — from browsing and booking to payment, maintenance, and reporting — with WhatsApp-first communication and automated email documents.

This version (v1.2) updates the hosting architecture from v1.1. The backend now runs on Hostinger Business (already paid), replacing the Render free tier. This eliminates cold starts, resolves the database connectivity risk, and unblocks node-cron for scheduled tasks — all at no additional cost.

| Field | Value |

| Version | 1.2 — Hostinger-First |

| Hosting | Vercel (frontend) · Hostinger Business (backend) |

## 6. Critical Architecture Decisions

### 6.1 Cron Jobs — node-cron (REINSTATED)

**Previous problem (v1.1):** Render's free tier spins down instances after 15 minutes of inactivity, making node-cron unreliable.

**v1.2 resolution:** The backend now runs on Hostinger Business — a paid, always-on hosting plan. The Node.js process runs continuously. node-cron is reliable and is the primary scheduler.

| Option | Cost | Reliable on Hostinger? | Decision |
|---|---|---|---|
| node-cron inside Express | $0 | ✅ YES — process stays alive | **CHOSEN** |
| cron-job.org ping to /run-jobs | $0 | Yes — external trigger | Backup / redundancy |
| Separate cron service | Variable | Yes | Not needed |

**Implementation:** Keep `cron-job.org` as a secondary trigger on `/api/cron/run-jobs` for redundancy, but node-cron is the primary scheduler.

---

### 6.2 PDF Generation — PDFKit (NOT Puppeteer)

PDFKit remains the correct choice regardless of hosting provider.

| Option | RAM Required | Decision |
|---|---|---|
| Puppeteer (headless Chrome) | 300–500MB | REJECTED — excessive RAM |
| PDFKit | ~10MB | **CHOSEN** |
| jsPDF | ~15MB | Alternative if needed |

---

### 6.3 Database — Hostinger Co-located (Risk Eliminated)

**Previous risk (v1.1):** Hostinger shared hosting was not designed for persistent remote database connections from an external server (Render). IP whitelisting, firewall rules, and latency were Medium-likelihood risks.

**v1.2 resolution:** The backend now runs on the same Hostinger account as the database. The connection is local — no firewall rules, no IP whitelisting, near-zero latency.

| Validation Step (v1.1) | Status in v1.2 |
|---|---|
| Whitelist Render IPs in Hostinger DB firewall | ✅ Not needed — same host |
| Test latency from external server | ✅ Not needed — local connection |
| Test connection pooling under load | Still recommended — run once in Week 1 |
| PlanetScale fallback setup | ✅ No longer required as primary fallback |

> **PlanetScale** is removed as a required fallback. It may still be documented as a contingency if Hostinger MariaDB has unexpected issues, but the risk is now Low.

---

### 6.4 Authentication — JWT with Refresh Token Rotation

*Unchanged from v1.1.*

Access tokens expire in 15 minutes. Refresh tokens expire in 7 days and are stored in the database (admins table). On each refresh, the old refresh token is invalidated and a new one is issued (rotation).

| Token Type | TTL | Storage | Rotation |
|---|---|---|---|
| Access Token (JWT) | 15 minutes | Memory / Authorization header | No |
| Refresh Token | 7 days | DB (hashed) + HttpOnly cookie | Yes — invalidated on use |

---

### 6.5 Email — Resend (NOT Brevo)

*Unchanged from v1.1.*

Resend provides 3,000 emails/month on the free tier, has a modern REST API, and integrates with Nodemailer using standard SMTP configuration.

### 6.6 Backend Deployment on Hostinger — Node.js Web App

Deploy the Express.js backend using Hostinger's built-in **Node.js Web App** feature (visible in hPanel → Add Website → Node.js Web App).

| Deployment Method | Recommended |
|---|---|
| GitHub integration (auto-deploy on push) | ✅ Yes — use for CI/CD |
| ZIP file upload | Fallback only |

**Entry point:** `server.js` or `app.js`
**Node.js version:** Select the latest LTS available in hPanel
**Environment variables:** Set all secrets (DATABASE_URL, JWT_SECRET, RESEND_API_KEY, CLOUDINARY_URL, SENTRY_DSN) in hPanel's environment variable manager — never commit them to the repo.

## 7. Security Requirements

| Requirement | Implementation | Package |
|---|---|---|
| Password hashing | bcrypt with cost factor 12 | bcryptjs |
| API authentication | JWT access tokens (15min) + refresh token rotation | jsonwebtoken |
| Input validation | Validate and sanitize all request bodies and params | express-validator |
| Rate limiting | 100 req/15min on public endpoints (booking, catalog) | express-rate-limit |
| HTTPS enforcement | Enforced at Vercel + Hostinger level — no HTTP traffic | Platform-level |
| File upload safety | Validate MIME type + file size limit (5MB) before Cloudinary upload | multer + file-type |
| SQL injection | Prevented by Prisma's parameterized queries — no raw SQL | Prisma |
| CORS | Whitelist only the Vercel frontend origin in production | cors |
| Error exposure | Never send stack traces to client in production | Custom error middleware |

## 9. Database Indexing Requirements

*These indexes are required from day one. The alert panel and reporting queries will be slow without them — Prisma does not add them automatically.*

| Table | Column(s) | Reason |
|---|---|---|
| bookings | car_id | Fleet utilization queries, availability checks |
| bookings | status | Alert panel filters overdue/active bookings |
| bookings | return_date | Overdue detection — node-cron queries this daily |
| bookings | customer_phone | WhatsApp link generation, client lookups |
| bookings | source | Booking source report filtering |
| cars | status | Catalog filtering — available / rented / maintenance |
| insurance_policies | expiry_date | Alert panel for expiring policies |
| maintenance_logs | scheduled_date | Alert panel for upcoming maintenance |

*Add these as `@@index` entries in your Prisma schema before running the first migration.*
