## 2. How Hostinger Runs Your Express.js App

Hostinger's managed Node.js hosting is **not traditional shared hosting**. It spins up a dedicated, always-running Node.js process for your app — not a PHP-style request-spawned process. This is what makes it suitable for your backend.

### What Hostinger manages for you (no manual config needed):
- **Reverse proxy** — Nginx routes traffic to your Express port automatically
- **npm install** — dependencies installed automatically on deploy
- **Build commands** — runs your `npm run build` (if applicable) on each deploy
- **HTTPS / SSL** — provisioned and renewed automatically
- **Process management** — restarts your process if it crashes

### What you control:
- **Entry point** — set `server.js` or `app.js` in hPanel build settings
- **Node.js version** — choose from 18.x, 20.x, 22.x, or 24.x (pick 20.x LTS)
- **Environment variables** — managed entirely via hPanel's env var manager
- **Build command** — e.g., `npm install` (or omit if no build step needed)

### File structure after deployment:
```
/home/{username}/domains/{yourdomain.com}/
├── nodejs/          ← your Express build files live here (NOT public_html)
│   ├── server.js
│   ├── node_modules/
│   └── ...
└── public_html/
    └── .htaccess    ← auto-generated by Hostinger to proxy traffic to your app
```

> ⚠️ **Important:** For backend apps (Express.js, NestJS), build output goes to `/nodejs/`, NOT `public_html`. Hostinger auto-creates an `.htaccess` to handle routing. Don't put your `server.js` in `public_html`.

## 5. Database — MariaDB Co-location on Hostinger

This is one of the biggest advantages of the Hostinger-first architecture. The MariaDB database is on the **same server** as your Express app, meaning:

- **Connection string uses `localhost`** — no remote DB firewall, no latency
- **No need to whitelist IPs** — local socket connection
- **Daily automatic backups** — included in the Business plan
- **Zero additional cost**

### Setting up your MariaDB database on Hostinger:

1. hPanel → **Databases → MySQL Databases**
2. Create a new database: e.g., `rentacar_prod`
3. Create a DB user and assign full privileges
4. Your `DATABASE_URL` for Prisma will be:
   ```
   mysql://db_username:db_password@localhost:3306/rentacar_prod
   ```

### Prisma with MariaDB:
Prisma supports MariaDB through the `mysql` provider. In your `schema.prisma`:
```prisma
datasource db {
  provider = "mysql"
  url      = env("DATABASE_URL")
}
```

> ⚠️ Run `npx prisma migrate deploy` (not `dev`) in production. Never run `migrate dev` on the live server.

### Connection Pooling:
Hostinger's shared infrastructure has process limits. Configure Prisma's connection pool conservatively:
```typescript
// In your Prisma client setup
const prisma = new PrismaClient({
  datasources: {
    db: {
      url: process.env.DATABASE_URL + '?connection_limit=5&pool_timeout=10'
    }
  }
})
```
A pool of 5 connections is safe for the Business plan. Monitor via the hPanel Resource Usage graphs.

## 6. node-cron — Reliability Assessment on Hostinger Business

This is the most critical architectural question for RentaCar, and the answer is **conditionally reliable with a known risk**.

### Why it should work:
Hostinger's managed Node.js hosting keeps your process **always running** (unlike Render's free tier that spins down). `node-cron` runs inside your Express process — as long as the process stays alive, cron jobs fire on schedule.

### Known risk — process restarts:
Hostinger will restart your Node.js process in these situations:
- **Deployment** — every GitHub push triggers a restart (brief downtime ~10-30 seconds)
- **Crash recovery** — if your app throws an unhandled exception and crashes
- **Plan resource limits hit** — if CPU/RAM limits are exceeded, the process may be killed
- **Server maintenance** — rare, but Hostinger may reboot shared servers

After a restart, `node-cron` re-registers all schedules automatically (since they're registered at startup). A job won't "miss" its schedule permanently — it will simply run at the next scheduled time after the restart.

### The dual-trigger strategy (already in your PRD — keep it):
Your PRD correctly identifies this risk and proposes using **cron-job.org** as a secondary HTTP trigger. This is the right call. Implementation:

```javascript
// In your Express app — a manual trigger endpoint
app.post('/api/cron/run-jobs', authenticate, async (req, res) => {
  await runOverdueCheck();
  await runInsuranceAlerts();
  await runMaintenanceAlerts();
  res.json({ ok: true, ran_at: new Date().toISOString() });
});

// node-cron — primary scheduler
cron.schedule('0 8 * * *', async () => {
  await runOverdueCheck();
  await runInsuranceAlerts();
  await runMaintenanceAlerts();
}, { timezone: 'Africa/Casablanca' });
```

Configure `cron-job.org` to POST to `/api/cron/run-jobs` daily at 08:05 Africa/Casablanca time, as a 5-minute-delayed backup. Use a shared secret header to authenticate the request.

## 7. CORS Configuration — Hostinger + Vercel Setup

Your Express backend runs on Hostinger, your React frontend on Vercel. CORS must be configured precisely:

```javascript
import cors from 'cors';

const allowedOrigins = process.env.NODE_ENV === 'production'
  ? [process.env.CORS_ORIGIN]  // 'https://rentacar.vercel.app'
  : ['http://localhost:5173', 'http://localhost:3000'];

app.use(cors({
  origin: allowedOrigins,
  credentials: true,           // required for refresh token cookies
  methods: ['GET', 'POST', 'PUT', 'DELETE', 'PATCH'],
  allowedHeaders: ['Content-Type', 'Authorization'],
}));
```

> ⚠️ Never use `origin: '*'` in production — this breaks `credentials: true` and is a security risk.

## 8. Port & Process Configuration

Hostinger assigns a port to your Node.js app and handles the reverse proxy. Your Express app should listen on the port Hostinger provides:

```javascript
// server.js
const PORT = process.env.PORT || 3000;

app.listen(PORT, () => {
  console.log(`RentaCar API running on port ${PORT}`);
});
```

Hostinger injects the correct `PORT` environment variable — your app does not need to know what the actual external port is.

## 9. Logging — Winston on Hostinger

Hostinger captures `stdout` and `stderr` from your Node.js process and makes them viewable in hPanel's log viewer. Configure Winston to write to stdout in production:

```javascript
import winston from 'winston';

const logger = winston.createLogger({
  level: process.env.NODE_ENV === 'production' ? 'info' : 'debug',
  format: winston.format.combine(
    winston.format.timestamp(),
    winston.format.json()
  ),
  transports: [
    new winston.transports.Console(), // Hostinger captures this
  ],
});

export default logger;
```

Do **not** write to log files on disk in production — Hostinger's managed environment has limited writable disk paths and log files will grow unbounded. Use stdout → hPanel log viewer → Sentry for the full observability stack.

## 10. Known Limitations of Hostinger Business (vs. VPS)

These are real constraints to be aware of, not dealbreakers for RentaCar's scale:

| Limitation | Impact on RentaCar | Mitigation |
|---|---|---|
| **Shared CPU/RAM** | Resource spikes can affect performance | Monitor via hPanel graphs; optimize heavy queries |
| **No SSH root access** | Can't install system packages | Not needed — Express.js + npm is fully self-contained |
| **Up to 5 Node.js apps** | Only 1 needed for RentaCar | No issue |
| **No `pm2` or process manager control** | Hostinger manages the process | Use Sentry to catch crashes; the platform auto-restarts |
| **No persistent disk writes** | Don't write files to disk long-term | Already handled — Cloudinary for images, no local file storage needed |
| **Process restarts on deploy** | ~10-30 seconds of downtime per deploy | Deploy during off-peak hours (nights); use rolling deploys if available |
| **Shared server** | Not dedicated infrastructure | Acceptable for a single-business rental platform at Morocco scale |
